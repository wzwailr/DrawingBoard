# GazBoard 与 DrawingBoard 已确认需求的逐项适配评估

核验日期：2026-10-19，资料截点约北京时间 17:15。范围：源码、发布元数据、公开 CI、当前项目实现与设计基线的只读研究；未安装或启动 GazBoard，未修改应用代码。

## 1. 决策结论

**GazBoard 可以改造成我们的应用，而且比从零写一个画布更合适；但与已经采用的“Electron + Excalidraw 编辑核心 + 自有交互层”相比，目前证据不支持整体切换到 GazBoard。建议继续当前 P0，把 GazBoard 作为模块参考和备用底座。**

关键原因不是它的功能少，而是缺口集中在我们最重视的交互与可靠性：

1. 现有自动识别是“松手后替换”，没有“末尾停顿 → 临时预览 → 松手提交”的流程。识别器的定向计算探针还发现了圆/椭圆反例。
2. 鼠标在边框、内部、文字之间的分工，双击文字入口，以及识别直线自动绑定，需要跨输入、命中、对象、历史修改。
3. 已有命名组合与纵向纸张，但没有满足本项目定义的独立命名区域；没有查到标准/轻手绘图形风格切换，以及对象对齐/等距排列的完整操作。
4. 本地保存实现有值得复用的资产管理和串行写入，但错误处理与退出策略需要加固，不能因为已有“自动保存”就直接验收。
5. 当前 Excalidraw 路线已经产生实际智能笔适配代码，尚未修改上游大型交互实现。这使最早“可能必须深改编辑器”的不确定性有所下降，但不等于 P0 已通过。

**例外条件：**如果接受 GazBoard 现有教学白板式交互，允许修改已确认产品规则，直接用或轻改 GazBoard 很可能更快。若严格保留 D01–D23，这会是一个持续维护的应用分叉，不能按“换皮、加快捷键”的工作量估算。两条路线均未完成同机、同任务的耗时与性能对照，因此不提供节省百分比或虚构人天。

## 5. 几项会改变选型判断的深入发现

### 5.1 智能笔不是现成能力只差一个 delay

GazBoard 的流程是：

`pointer up → finishStroke → 添加原始笔迹（历史一）→ recognize + fitError → 删除笔迹/添加 shape（历史二）`。[G11]

我们需要：

`绘制 → 指针末尾停住且仍按着 → 只显示候选预览 → 松手才提交原迹或图形 → 后续仍可恢复来源`。

必须修改触发、临时渲染、历史提交和取消语义；并连接文字与连线入口。原来的“双事务”有明确用意：一次撤销还原笔迹。我们技术方案提出的“一次提交单元 + 独立恢复笔迹”是另一种选择，不能直接把两者混在一起，也不能把差异称为上游 bug。

### 5.2 识别器：实际运行了七个定向输入，发现可重现反例

在工具的 V8 内存环境中运行固定提交的 `util.js` 与 `recognize.js` 原函数，只移除 ES module 的 import/export 声明；按真实入口使用 `confidence > 0.6 && fitError < 0.055`。未改 GazBoard 文件、未安装应用、未模拟鼠标设备。[识别源码][G31]、[结果数据](gazboard-recognizer-probe.json)

| 合成输入 | 原分类结果 | fitError（约） | 实际入口会否接受 | 解释 |
| --- | --- | --- | --- | --- |
| 正圆 200×200，129 点 | circle，confidence=0.6 | 0.00767 | 否 | 返回兜底 0.6，但调用方要求严格大于 0.6 |
| 横向椭圆 300×200，129 点 | hexagon，confidence=0.7 | 0.02992 | 是 | 会接受为六边形，与此输入意图不符 |
| 横向椭圆 400×200，129 点 | pentagon，confidence=0.7 | 0.03930 | 是 | 会接受为五边形 |
| 横向椭圆 600×200，129 点 | triangle，confidence=0.85 | 0.08048 | 否 | 拟合检查拦住误分类 |
| 矩形 300×160，129 点 | rect，confidence=0.88 | 0.00218 | 是 | 该样例正常 |
| 反向直线，65 点 | line，confidence 接近 1 | 0.00272 | 是 | 保留起终点方向 |
| 小圆 12×12，129 点 | null | — | 否 | 源码有世界坐标尺度阈值 |

这不是“七个案例的总体准确率”，也不是所有圆都失败。真实采样起点、噪声、数量、缩放会改变结果。它足以否定“直接复制当前识别器即可满足我们的圆/椭圆规则”。**本轮没有对 Excalidraw 运行同一套轨迹，不能据此宣称后者识别率更高。**

另外，`fitError` 对原始点逐个遍历候选轮廓；多边形轮廓密度随世界坐标边长增加。超长笔画、极端缩放的成本应另测，不给未经测量的性能结论。

### 5.3 命名组合值得借鉴，但不应冒充命名区域

GazBoard 的 `groupId/groupName` 存在成员对象上，显示边界由成员包围盒即时计算；已有组再组合会被摊平到一个新组。[G9][G10]

我们的产品文档明确区分“大矩形、组合、命名区域”。命名区域是独立的页面/方案范围，用于组织、定位、展示与导出。区域边界与成员移动的细节仍有待验证，但不能直接把教学纸张或命名组合算作完全覆盖。

改造可利用组的选择、边界提示、名称显示；还要增加区域身份、边界、成员语义，以及历史、复制、文件、展示、导出的传播路径。当前 Excalidraw 也不能把默认 frame 行为直接等同于我们全部规则，尤其自动归属需要限制。

### 5.4 连接线是很有价值的模块，但入口策略不同

`connectors.js` 已包含目标引用、组目标、几何停靠、直线/折线/曲线及箭头；目标消失时可保留自由端回退。这是比从零写连线系统更扎实的参考。[G19]

但专门线工具的绑定流程与智能笔识别流程分开；识别结果创建的是普通 shape。仍需接入“两端绑定才默认带箭头”的策略。还要评审其沿中心方向重新停靠的方式是否符合我们的端点预期；具体固定相对锚点属于方案细化，不是必须照搬当前实现的理由。

对现有 Excalidraw 路线，优先借它的几何边界案例和回归用例；**不建议把 GazBoard connector 对象也塞入现有场景，形成两套绑定与撤销系统。**

### 5.5 保存机制有实用设计，也有必须处理的失败路径

值得借鉴：串行保存、图片资产拆分、图片缺失时保留引用、首次恢复时防止异步旧结果覆盖已开始的编辑。[G8][G21]

需要加固：

| 路径 | 源码事实 | 影响与证据边界 |
| --- | --- | --- |
| 切换前保存 | `saveBeforeLeaving()` 捕获保存错误后继续；`loadBoard()` 随后加载另一个文档 | 不能以“显示了失败提示”替代对尚未保存内容的保留。未做故障注入，不能写成已观察到用户数据丢失。[G21] |
| 保存状态确认 | `_persistNow()` 用文档 ID 防止跨画布更新状态，但成功后直接清 `_unsaved` 并显示 Saved，没有对同画布修订号做比较 | 保存等待期间又编辑，较旧写入可能错误清除当前脏状态。是否最终被下一次保存补上取决于时序，需要定向测试。[G21] |
| 写文件回退 | `writeAtomic()` 先写临时文件；rename 失败时直接 writeFile 原路径 | 该回退失去“替换失败仍保留旧文件”的保障，不能整体称为已验证的原子保存。[G22] |
| 文档与最近指针 | boards.save 中文档与 last-board 用 Promise.all 分别写 | 并不因为同一个 IPC 就成为文件系统事务；恢复入口要能处理两者不同步。[G22] |
| 退出确认 | 主进程最多等待 2 秒；renderer flush 捕获错误后返回，preload 随后仍发送 app:flushed | 保存失败仍可能退出。需改成带结果确认，保留未保存内容与用户可见的重试/导出入口。[G32] |

上述属于源代码风险分析，未执行崩溃、磁盘满、权限拒绝测试。我们的当前路线同样需要满足对应可靠性验收；方案写了 seq/备份/错误状态并不代表已完成。

### 5.6 中文编辑与展示需要按我们的场景校准

文字编辑已有 contenteditable、富文本和中文字体回退。普通 Enter 使用 `!isComposing` 保护，但 Escape 直接 cancel，Ctrl+Enter 直接 commit；这两个分支没有相同保护。需要真实 Windows 中文输入法验证，并明确“取消候选字”与“取消整个文本会话”的区别。[G17][G23]

展示模式有 UI 隐藏、页面适配和临时指示能力，但允许重新唤回工具继续编辑。这适合教学，不满足我们的“讲解时避免普通鼠标动作改内容”。可复用展示外观与临时指示，增加只读门控即可；这项通常比改智能笔更局部。[G29]

## 6. 如果以 GazBoard 为底座，需要改动哪些模块

复杂度为相对判断，不是工期；取决于最终规则细化和回归结果。

| 工作包 | 主要涉及的现有代码 | 能保留什么 | 需要自有的部分 | 相对范围 |
| --- | --- | --- | --- | --- |
| Windows 待命与恢复 | main.js、preload.js、app.js | 窗口、单实例、显示器检查 | 热键/托盘/收起、保存确认、视角策略 | 中 |
| 智能笔与识别 | core/tools.js、recognize.js、surface.js、store.js | 采样、湿墨、对象/历史基础 | 停顿状态机、预览、可信分类、原迹来源、提交 | 高 |
| 命中与文字 | core/hit.js、tools.js、ui/textedit.js、app.js | 几何命中、现成文本布局/编辑 | 边框/内部规则、双击分工、IME 与快捷键优先级 | 高 |
| 连线 | connectors.js、tools.js、app.js、transform.js | 路由、停靠、目标引用 | 智能笔接入、双端箭头规则、完整回归 | 中 |
| 布局与区域 | store.js、surface.js、render.js、export.js、UI | 组合、图文、选择与包围盒 | 独立区域、成员操作、对齐/等距、范围导出 | 高 |
| 两种图形风格 | render.js、export.js、样式 UI | 标准图形绘制 | 轻手绘几何、保存/导出一致、原始笔迹隔离 | 中至高 |
| 可靠持久化 | main.js、preload.js、app.js、store.js | 资产拆分、串行写入、恢复和库接口 | 修订确认、失败保留、校验/备份/恢复流程 | 高 |
| 轻量工作区 | toolbar.js、panels.js、contextmenu.js、CSS | 浮动工具、弹出属性、搜索 | 我们的入口层级、提示、最近抽屉 | 中 |
| 展示与交付 | ui/present.js、app.js、export.js、board-export.js | 指示、PNG/PDF/图片复制/文件 | 展示输入门控、新字段往返、范围和品牌 | 低至中，区域部分另计 |

GazBoard 是一套完整应用，不是专门的嵌入式编辑器 SDK。好处是数据和输入完全在自己能改的源码里，不受 SDK 扩展点限制；代价是上述改动会穿过多个共享中心模块，要自己维护整个应用分叉。

检查版本中，app.js 约 5,594 行，tools.js 约 3,139 行，panels.js 约 2,625 行。这里引用规模只是说明改动位置集中且交叉，**不以行数或 JavaScript 语言判断代码好坏**。无需为采用它而先整体改写成 TypeScript。

## 7. 与当前方案公平比较

| 维度 | 改造 GazBoard | 当前 Electron + Excalidraw |
| --- | --- | --- |
| 现成应用完整度 | **占优**：本地库、搜索、PDF、可编辑文件、展示、安装发布都已有 | 仍在 P0，宿主产品功能有相当一部分待做 |
| 对输入控制的自由 | 自有 Canvas 输入链，可直接修改，定位更直观 | 宿主捕获输入 + custom tool；依赖上游事件和场景契约，仍需完整 P0 验证 |
| 已确认智能笔规则 | 要替换释放识别入口，增加预览状态机；识别器有已测反例 | 已有状态机、预览与提交实现及针对性测试代码；分类质量和完整设备路径不能直接宣布通过 |
| 图形编辑、对齐、分布、手绘风格 | 一部分需要补，另一些要持续维护 | 引擎已有相应基础；frame/分组/标签仍要适配我们的语义 |
| 文字 | 富文本功能更完整，但入口与 IME 需改 | 当前实现选择较窄文本交互，减少范围；同样需要中文真机验收 |
| 连接线 | 自有模型简单可读，几何模块值得借鉴 | 使用同一引擎绑定/历史；当前已有连接策略适配代码，尚未据此判验收 |
| 本地保存和导出 | **现成模块更多**，但要修失败策略、补新增语义 | 定义较严格，可按最小需求实现；尚未完成可靠性证明 |
| 长期维护 | 所有行为可控，但需维护渲染、文本、历史、导出和 Windows 产品分叉 | 可复用上游编辑能力，但固定版本构建、内部包接口和升级补丁仍是维护成本 |
| 快开、后台内存、长画布性能 | 未同机测量 | 未完成同口径比较；不能根据代码量或安装包大小判胜负 |
| 现在换底座的收益 | 少做一部分周边功能，多做核心交互和模型适配 | 已有智能笔接入证据可继续验证；不是仅靠“已经投入了时间”支持它 |

**当前项目不是从零造图形引擎。** 本轮读取了 [适配器](../../../src/renderer/editor/adapter.ts)、[智能笔层](../../../src/renderer/ink/SmartPenLayer.tsx)、[笔迹对象转换](../../../src/renderer/editor/stroke-element.ts)、[识别接入](../../../src/renderer/ink/recognizer.ts)和 [vendor 说明](../../../vendor/README.md)。

此刻没有修改上游 App.tsx/私有输入处理；记录的唯一上游补丁是本地字体路径配置时省略 CDN 回退。已有桌面用例检查“直接松手为 freedraw、预览时场景为空、松手后一个 rectangle、预览后移动恢复原笔迹”。这些是实现与测试设计证据，本轮没有重跑它们。[当前测试文件](../../../tests/desktop/smart-pen.spec.ts)

也不能把这一路线描述成“完全只用稳定公开 API、零上游耦合”：适配还使用固定源码下的 `@excalidraw/element`、`@excalidraw/math` 构造与识别能力。未来升级需重新验证。现有 P0 文档记载的 3/3 快照测试、离线 Electron 检查、11/11 手势单元测试只是此前记录，且 T02 状态栏仍写进行中；不是本轮新鲜完整验收。

## 8. 哪些借用，哪些需要我们设计

### 可以优先借鉴机制或移植局部实现

1. **最近画布模型**：最近打开记录与画布文件分离、缺失项保留提示、搜索和重命名联动。可独立适配，耦合较小。[G24]
2. **连接线几何和边界用例**：形状/组合端点、目标删除后的回退、路由与箭头。现路线以参考算法和测试为主，继续使用 Excalidraw 场景对象。[G19]
3. **导出链路设计**：当前内存快照、图片解析、缺图拒绝、静态输出边界、去掉机器私有 origin 路径。PDF 输出形式与当前方案兼容。[G26][G28]
4. **窗口位置恢复和临时指示**：已有逻辑可以参考，仍需适配我们宿主与展示门控。[G7][G29]
5. **数据保护的正向细节**：异步恢复的修订检查、资产缺失保留引用；同时避免复制失败继续切换、直接覆盖回退等策略。[G8][G21][G22]

### 不适合原样搬入

- 当前 recognize.js 及其接受门槛：先处理已发现反例，再基于真实鼠标轨迹评估。
- 整套 tools.js、app.js：会把教学、触控、专用形状工具、鼠标模式等已有策略一起带入。
- 现有保存/退出链：需按我们确认的“失败不静默丢内容”结果重新约束。
- 把命名组合改显示名称就充当命名区域。
- 在 Excalidraw 内并行引入第二套 GazBoard scene/history/connector 模型。

### 必须由我们掌握的产品规则

智能笔意图与停顿策略、边框/内部/文本的鼠标分工、双端箭头规则、独立区域语义、从唤出到收起的保存与焦点策略、轻量工作区的信息层级。

这里的“我们设计”指需要为本产品做取舍、实现和验证，**不宣称这些概念是行业原创**。按住规整、无限画布、连接线、本地桌面白板都有先例；开发必要性最终还取决于整段工作流是否更顺畅。

## 10. 建议的后续决策门槛

本轮不切换底座，不调整另一个实施分支。

1. **继续当前 P0 的核心门槛**：鼠标绘制/停顿/文字/绑定/恢复/历史必须能一起成立，重点核查私有交互补丁是否扩散。已有局部进展不能代替完整验收。
2. **若当前路线通过**：保留 Excalidraw，按上节借鉴 GazBoard 的周边模块与边界用例；无需再搭一整套竞争架构。
3. **若当前路线失败**：记录具体失败（例如无法控制事件、必须复制大型交互实现、对象绑定和历史不能一致），再在独立副本做 GazBoard 最小改造实验。只验证同一组高风险链路，不先搬齐所有教学功能。
4. **换底座必须有对照证据**：相同 Windows 环境、相同画布、相同鼠标任务，比较完成时间、误触、丢内容风险、隐藏后唤出、冷启动与后台资源。该测量现在没有，不能仅凭功能清单决定。

本报告给出的推荐强度为“中等”：源代码差异和定向识别反例明确，整体改造成本、真人体验和性能仍有未验证部分。GazBoard 的完整应用基础是真优势，当前 Excalidraw 路线的编辑能力与已存在适配也是真优势；目前后者更贴合保留已确认规则的方向。
